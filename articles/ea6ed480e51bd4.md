## 概要

最近は気温も上がり、ほどよく暖かくて過ごしやすい日が続いています。お昼寝が心地よい季節ですね。いつまでも寝続けられそうです。寝続けると言えば、自作OS の Urthr ではまだプライマリコアしか動いていません。サブコアはずっと寝続けたままです。人間様が寝るのは良いですが、CPU 如きが寝続けるなんて8億年早いです。さっさと叩き起こしてしまいましょう。ということで、今回はサブコアを起動して最低限のセットアップだけすることを目標にします。

## 起動の方法

Urthr は現在のところ Raspberry Pi 5, Raspberry Pi 4B on QEMU, QEMU virt モデルの3つをターゲットにしています。サブコアの起動の方法はターゲットによって異なります:
- **Spin Table**: Rasperry Pi 4B
- **PSCI**: Raspberry Pi 5 と virt モデル

### Spin Table

**Spin Table** を使うメソッドでは、サブコアは EL1 または EL2 の状態でループに入っています。例として RPi4b on QEMU の場合には以下のような命令でスピンしています:

```c
0x00000300:  d2801b05  movz     x5, #0xd8
0x00000304:  d53800a6  mrs      x6, mpidr_el1
0x00000308:  924004c6  and      x6, x6, #3
0x0000030c:  d503205f  wfe
0x00000310:  f86678a4  ldr      x4, [x5, x6, lsl #3]
0x00000314:  b4ffffc4  cbz      x4, #0x30c
0x00000318:  d2800000  movz     x0, #0
0x0000031c:  d2800001  movz     x1, #0
0x00000320:  d2800002  movz     x2, #0
0x00000324:  d2800003  movz     x3, #0
0x00000328:  d61f0080  br       x4
```

WFE で待機した後、`0xD8 + 8 * core` の値を読み、`0` であれば再度これをループします。すなわち、コアNを起動させるためには `0xD8 + 8 * N` にエントリポイントのアドレスを書き込んであげれば、ループを抜けて X1~3 をゼロクリアした後、指定したアドレスにジャンプします。今回はこいつは主役ではないので、どうでもいいです。

### PSCI

どうやら、RPi5 では PSCI がサポートされているようです。EL3 FW は案の定 [ATF (TF-A)](https://github.com/arm-software/arm-trusted-firmware) です。GPU がカーネルをロードして CPU を起動するのに、いつ ATF がロードされるのだろうかと思っていましたが、[この記事](https://vengineer.hatenablog.com/entry/2023/10/04/080000) によると `[0, 0x8_0000)` の領域に ATF をコピーしてくれるらしいです。実際、Linux の DeviceTree を読んでもこの領域は ATF 用に予約されていました:
```dtf
/// arch/arm64/boot/dts/broadcom/bcm2712.dtsi
	rmem: reserved-memory {
		ranges;
		#address-cells = <2>;
		#size-cells = <2>;

		atf@0 {
			reg = <0x0 0x0 0x0 0x80000>;
			no-map;
		};
        ...
	};
```

ところで、この領域は単純に DRAM にあります。Raspberry Pi 5 にはおそらく CPU Security State に応じて DRAM を保護する仕組みが存在しないため、この ATF 領域は EL1 から書き換えることが可能です。つまり、**ATF を任意に書き換えることで EL3 で任意のコードを実行することが可能と思われます**。実際、サブコア対応をするまではカーネルイメージは GPU によって `0x20_0000` に配置されるものと勘違いしていました。BL のログでも以下のようになっています:
```
  7.11 fs_open: 'armstub8-2712.bin'
  7.61 Loading 'kernel_2712.img' to 0x00000000 offset 0x200000
  7.31 Read kernel_2712.img bytes    90224 hnd 0xe570
  7.63 MESS:00:00:07.633733:0: Kernel relocated to 0x80000
  7.63 MESS:00:00:07.638901:0: Device tree loaded to 0x2da7c600 (size 0x13976)
```

これを勘違いしていて、`0x20_0000` に書いてあるものと思っていました。しかし、実際には FS から `0x20_0000` にロードされた後、`0x8_0000` に再配置されているようです (ここでいう再配置は、リンカが行う relocation ではなく、本当にイメージをコピーし直している模様)。ついでに、ATF の実体である `armstub8-2712.bin` も FS から読み込まれていそうな雰囲気を感じますね。
自分はロードされるアドレスを勘違いしていたものの、最初にロードされるチェインローダーの Wyrd はほぼ PIC なので、偶然動いていたことになります。しかしながら、Wyrd は初期メモリアロケータに作業用領域として `[0, 2MiB)` の領域を割り当てていました。完全に ATF を上書きしてしまっていたため、PSCI が動きませんでした...。このことからも、RPi5 では ATF を自由に書き換えられそうなことが分かりますね。

話を戻して、PSCI は `CPU_ON` という関数を提供しているため、RPi5 ではこいつを使って CPU を起こします。SMC64CC が使えます。

## MPIDR

Raspberry Pi 5 では各コアの番号は **MPIDR** の Affinity 1 に入っているようです。Affinity 0 はどのコアも `0` です。Core#1 の場合は Affinity 1 が `1`、Affinity 0 が `0` です。`CPU_ON` では起動対象の CPU の Affinity を指定する必要があるので、間違えて Affinity 0 に `1` などを指定しないようにしましょう。

## 起動フロー

サブコアの起動は以下の流れで行います:
- 1: サブコアエントリポイントを論物一致でマップする
- 2: ブート用のデータを埋める
- 3: PSCI `CPU_ON` する
- 4: プライマリコアはカウンタが増えるまで待機する
- 5: サブコアが起動してカウンタを増加させる

1 について、サブコアの起動中に Core#0 と同じページテーブルで MMU を有効にするため、MMU無効・有効の両方の状態で実行できる必要があります。2 について、ブート用のデータは以下のとおりです:

```zig
/// Secondary cores use this data to set up their execution environment
const SmpBootData = extern struct {
    /// TTBR0.
    ttbr0: u64,
    /// TTBR1.
    ttbr1: u64,
    /// TCR.
    tcr: u64,
    /// MAIR.
    mair: u64,
    /// Virtual address of the kernel subcore entry point.
    entry: u64,
    /// Virtual address of the stack for the secondary core.
    stack: u64,
};
```

これらの値は、`entry` と `stack` を除いてプライマリコアの値をそのままコピーして使います。サブコア起動直後のスタブコード内でこれらの値を使って MMU を有効化し、指定したスタックで指定したエントリポイントに飛ぶという流れです。

## デバッグ

完璧な流れだと思ったのですが、実際に試してみると QEMU (virt) では動くものの、**実機でのみサブコアが動きませんでした**。最初のスタブコードに到達しているかどうかすらわかりません。PSCI `AFFINITY_INFO` を呼んでみると ON に変化していることは確認できているものの、どこで止まっているのかは分かりませんでした。

### Raspberry Pi Debug Probe

流石にこれ以上は何もわからないため、観念して [Raspberry Pi Debug Probe](https://www.raspberrypi.com/documentation/microcontrollers/debug-probe.html) を買いました。Amazon で 3000 円程度、当日中に届きました。OpenOCD の設定ファイル等については [こちら](https://www.raspi.jp/2024/03/raspberry-pi-5-hardware-debbuging/) を参考にしました。Debug Probe 自体も Raspberry Pi Pico でできているらしいです。UART と SWD 用のポートがついています。RPi5 は JTAG ではなく SWD です (CMSIS-DAP SWD)。付属されているコネクタも 3pin debug - 3pin debug / 3pin debug - 0.1" jumper (male) / 3pin debug - 0.1" jumper (female) と3種類あるので、RPi5 以外にも使えそうです。ただし、RPi5 では端末側の UART ポートが SWD ポートも兼ねており、同時に使うことはできません。GPIO にも UART 機能がありますが、こっちは以前の記事でも書いたように RP1 South-Bridge 経由で設定する必要があるので使い勝手が悪いです。というわけで、仕方なくログ無しでデバッグすることにしました:

![](/images/debug-probe.jpg)

OpenOCD が GDB server を建ててくれるので基本的にはいつもどおりデバッグできるのですが、使っていて気になった点は以下です:
- 取得できないシステムレジスタが多い
    - CPSR, ELR, ESR, SPSR 以外は取れなかった
    - TTBR が取れないのは不便だが、マップされていないアドレスを `x` コマンドで表示しようとすると server 側でエラーが表示されるので、マップされているかは分かる (client 側は `0` が返された扱いになるっぽい)
- 起動直後からアタッチできない
    - 起動直後にアタッチしておくと、例外が発生して進まなくなるっぽい？
    - そのため kernel まで到達してから OpenOCD を立ち上げる必要があった

### エラー発生部分

まず、エントリポイントであるスタブコードの先頭に busy loop を入れてみたところ、サブコアへのアタッチ時にそこで止まっていることが分かりました。よって、**エントリポイントまでは到達しているようです**。スピンループから PC を1つずつ (4つずつ) 進めてステップ実行したところ、**Boot Data の中身が変な値になっている**ことがわかりました。スタブコードにおける Boot Data のロードは以下のようになっています:

```S
  // Calculate VA-PA offset.
  adr  x10, 1f
  ldr  x11, =1f
1:
  sub  x11, x11, x10 // VA - PA offset

  // Compute physical address of the boot data.
  ldr  x10, =_boot_data
  sub  x10, x10, x11

  // Load the boot data.
  ldr   x0, [x10, #0]   // TTBR0_EL1
  ldr   x1, [x10, #8]   // TTBR1_EL1
  ldr   x2, [x10, #16]  // TCR_EL1
  ldr   x3, [x10, #24]  // MAIR_EL1
  ldr   x4, [x10, #32]  // Entry
  ldr   x5, [x10, #40]  // Stack

  // Configure MMU.
  msr   TTBR0_EL1 , x0
  msr   TTBR1_EL1 , x1
  msr   TCR_EL1   , x2
  msr   MAIR_EL1  , x3
```

この時、Boot Data の中身を見ると以下のようになっていました:
```
(gdb) p/x &_boot_data
$2 = 0xffffff0000118b30 // 仮想アドレス。これの物理アドレスが X10 に入っている
(gdb) x/2gx $x10
0x518b30:       0xd65775bb87b90ebb      0x05147d9646148dbc
```

ここには TTBR0_EL1 と TTBR1_EL1 が入っているはずなので、明らかにおかしいです。このまま MMU を有効化してしまうと、アドレス解決ができずに例外が発生してしまいます。EL1 スタブコードではブート中にのみ使われる一時的な例外ベクタとしてスピンループするだけの関数たちをセットしています。MMU の有効化後の ISB 命令でその例外アドレスにジャンプしていることが確認できました。また、例外ベクタの最初の命令実行時にもやはりアドレス解決ができず、再度例外が発生します。**ただし今回は EL1 ではなく EL3 の例外ベクタ (`0x200`) にジャンプするようです**。Aarch64 には x64 みたいな Double Fault の仕組みがあるのかは知りませんが、まぁそういうものなのかもしれません。

ここでまず疑うべきはなのはキャッシュコヒーレンシですね。プライマリコアから Boot Data を書き込んだ後、そのデータはキャッシュに乗るため、プライマリコアは以下のように `DC CSW` を使ってキャッシュを clean しています:

```zig
pub const CacheInfo = struct {
    /// Total size of the cache in bytes.
    size: usize,
    /// Cache line size in bytes.
    line_size: usize,
    /// The number of ways.
    ways: usize,
};
/// L1 d-cache.
const l1_dcache = CacheInfo{
    .size = 64 * 1024,
    .line_size = 64,
    .ways = 4,
};
/// L2 cache.
const l2_cache = CacheInfo{
    .size = 512 * 1024,
    .line_size = 64,
    .ways = 8,
};

// L1 d-cache clean
for (0..l1_dcache.sets()) |set| {
    for (0..l1_dcache.ways) |way| {
        const op =
            @as(u64, way) << (32 - l1_dcache.waysShift()) |
            @as(u64, set) << l1_dcache.setsShift() |
            @as(u64, level) << level_shift;
        asm volatile ("dc csw, %[op]"
            :
            : [op] "r" (op),
            : .{ .memory = true });
    }
}
// L2 cache clean も同様に...
```

Raspberry Pi 5 のキャッシュは以下のようになっています:
- L1 d-cache: 64 KiB
    - Line Size: 64 bytes
    - 4 ways
- L2 cache: 512 KiB
    - Line Size: 64 bytes
    - 4 ways

とりあえず Boot Data に限らず全データキャッシュをフラッシュするために、全セットx全wayに対して DC CSW を呼び出すようにしていました。それにも関わらず Core#1 からは見えない。うーむ、キャッシュは関係ないということだろうか...。

### DC ICVAC で試す

ChatGPT と Claude には何回もデバッグさせたのですが、あいつらは駄目でした。気晴らしに一旦 **DC ICVAC** で試してみることにしました (Invalidate する必要はないので CVAC でも同じです)。プライマリコアで以下のように、`_boot_data` の仮想アドレスを使ってキャッシュをクリーンしてみます:
```zig
asm volatile(
    \\dc icvac, %[data]
    \\dsb sy
    : [data] "r" (@intFromPtr(&_boot_data))
    : : "memory"
);
```

すると、サブコアから見た Boot Data に以下のような変化がありました:
```
(gdb) x/5gx 0x517b30
0x517b30:       0x0000000000080000      0x0000000000081000
0x517b40:       0x4878f7d833133380      0x1f5a899062732c76
0x517b50:       0xc33e81e9be0a1f2d
```

**先頭 0x10 bytes の TTBR0_EL1 と TTBR1_EL1 は正しいですが、それ以外の値は未だに壊れています**。しかしながら、大きな進展です。正しいデータと壊れているデータの境界は `0x517B40`、64 bytes 境界です。L1/L2 cache のキャッシュラインのサイズが 64 bytes であることに一致します。つまり、**DC CVAC を使った場合は (そのキャッシュラインは) 正しくフラッシュされているということが分かります**。あとは Boot Data をキャッシュラインにアラインして配置するなり、Boot Data がまたがる全ラインを DC CVAC するなりで動くことになります。
しかしまだ謎は残ります。なぜ DC CSW では動かなかったのでしょうか...。

### PoC に到達してなかった

答え合わせタイムです。DC CSW で Boot Data がサブコアから見えていなかった原因は、**単純に L3 キャッシュの存在を忘れていたからでした**。上記の DC CSW により L1/L2 キャッシュは追い出されていましたが、**追い出し先が DRAM ではなく L3 に入ってしまっていたようです**。つまり PoC までは到達していなかった...。いくらシステム全体で共有される L3 キャッシュとは言え、まだ MMU の有効化及びキャッシュの有効化をしていないサブコアには関係なかったようです。
Raspberry Pi 5 に載っている L3 キャッシュは 2048 KiB, Line Size 64 bytes, 16 ways です:

```zig
const l3_cache = CacheInfo{
    .size = 2048 * 1024,
    .line_size = 64,
    .ways = 16,
};
```

これを先程の L1/L2 に加えて DC CSW してあげたところ、無事にサブコアからも Boot Data の正しい値が見えて全サブコアが起動しました。やった〜。

## アウトロ

やっぱりキャッシュは難しいね。

ちなみに、PSCI `CPU_ON` するまでのサブコアは本当に電源断されているわけではなく、スピンテーブル同様に parking halt 状態になっていました:

```
   0x1ac4:      lsl     x0, x0, #3
   0x1ac8:      mov     x2, #0x108                      // #264
   0x1acc:      add     x0, x0, x2
   0x1ad0:      mov     x1, #0x0                        // #0
   0x1ad4:      str     x1, [x0]
   0x1ad8:      wfe
=> 0x1adc:      ldr     x1, [x0]
   0x1ae0:      cmp     x1, #0x1
   0x1ae4:      b.ne    0x1ad8  // b.any
   0x1ae8:      mov     x0, #0x100
   0x1aec:      ldr     x1, [x0]
   0x1af0:      br      x1
```

まぁおそらく ATF 上の「どこか」にそういうコードがあるんでしょう。それにしても、やっぱり Debug Probe は便利だなぁ。サブコアがひとまず起動したのでこれ以降は例外ハンドラから情報を取れるものの、こういう初期開発だと有用です。
